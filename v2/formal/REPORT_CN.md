## 1. 这里的“形式化验证”意味着什么——以及它不能意味着什么

KIP 2.0 清晰地划分为具有截然不同可验证性的各层：

| 层级 | 是否可验证？ | 所用方法 |
| --- | --- | --- |
| 文法 (KQL/KML/META EBNF) | 是，机械可验证 | 静态一致性分析（本套件） |
| 核心数据模型不变式 (§5–§23) | 是，有界可验证 | Alloy 6 时序模型检测 |
| 事务运行时 (§32–§36) | 是，有界可验证 | TLA+ / TLC 显式状态模型检测 |
| 治理评估 (§29–§31) | 是，有界穷举可验证 | 穷举判定过程检测 |
| 认识投影*策略* | 否——有意未作规定 | （仅限框架属性） |
| 作为行为的记忆/学习 | 否——属于实证性、Brain 层面 | §21.3 风格的消融基准测试，而非证明 |

两条适用于下述所有结果的长期注意事项：

1. **有界的，而非无界的**：Alloy/TLC 在有限范围内（小范围假设 / small-scope hypothesis）验证所有行为。它们在范围内具有可证伪完全性：任何在 ≤ N 个原子/步骤内可表达的不变式违反都会被发现。
2. **模型与规范的差距**：这些模型形式化的是我们对文本规范的*解读*。若规范存在歧义，歧义本身将作为一项发现进行报告，而非被隐式解决。

## 2. 套件 1 — 核心数据模型的 Alloy 6 时序模型

`alloy/kip-core.als` 将概念 (Concept) / 命题 (Proposition) / 断言 (Assertion) / 证据 (Evidence)（+ 胶囊导入 Capsule import、通过活动 Activity 的派生 derivation、权限类别 authority classes、合并 merge）建模为一个状态迁移系统。规范所强制的不可变性（§6.3 `_system.origin`，§12.5 命题元组，§13.7 断言负载 payload）在结构上进行编码：从构建上这些字段*无法*被更改。可变状态（元素创建、生命周期状态、`merged_into`、权限 authority、提权审计 elevation audit）仅通过对规范写入操作进行编码的事件演变。

### 检查的定理（预期 UNSAT = 在范围内无反例）

| # | 性质 | 规范 | 结果 |
| --- | --- | --- | --- |
| C1 | 规范命题唯一性在所有不包含合并的操作交错下均得以保持 | §12.3–§12.4 | **已验证** |
| C2 | 历史是单调的——任何操作都不会删除元素（物理清除 purge 排除在范围外） | §11.1, §13.8, §15.5 | **已验证** |
| C3 | 无生命周期复活：已撤回 (retracted) / 已废弃 (superseded) / 已过期 (expired) 的断言永不返回活跃状态 (active) | §14 | **已验证** |
| C4 | 同空间闭包 (Same-Space closure) 在每次操作后均成立，包括派生写入 | §5.3 | **已验证**（模型修复后——见 F3） |
| C5 | 防环合并保持规范解析良定义 | §11 (已修复) | **已验证** |
| C6 | 带有导入祖先的元素，除非其谱系中存在显式提权，否则权限永远不会超过描述性 (Descriptive) 权限 | §29.6, §31.4, §31.5 | **已验证** |
| C7 | 派生永远不会造出新的认识根（无证据乘法 / No Evidence Multiplication） | §23.1–§23.2 | **已验证** |

### 见证轨迹（预期 SAT = 场景可表示/可达）

| # | 场景 | 规范 | 结果 |
| --- | --- | --- | --- |
| R1 | 合并确实可能导致两个存活的命题在同一个规范元组上发生碰撞——这就是 §11.4 的 MAY-consolidate 条款必须存在的原因 | §11.4 | **已见证** |
| R2 | **发现 F1**：原样书写的 §11 允许出现合并环（A→B，然后 B→A），导致规范解析未定义 | §11 | **已见证** |
| R3 | 若派生忽略了输入权限（违反 §29.6），导入的内容将在没有提权的情况下被洗白为可执行 (Executable) 权限——这证明了 §29.6 是承重规则 | §29.6 | **已见证** |
| R4 | 三个支撑证据项坍缩为一个单一的独立根：复制/派生链不会造出相互佐证 | §23.1, §23.4 | **已见证** |

C6 值得特别强调：它是在创建/派生/导入/提权/合并/生命周期事件的*所有*交错执行上成立的归纳安全性质——正是 Architecture §16.2 所承诺的“源头无法通过摘要/整合链被洗白”的保证。与之对应的 R3 见证轨迹表明，一旦实现不是严格根据输入谱系来计算派生权限，该保证就会立即失效。

**范围与开销**。检查在 2 个 Space、2 个 Principal、每个种类元素范围为 2–4 个原子的条件下，针对 6–8 步的轨迹（使用 glucose 后端）运行。大多数证明目标在数秒内解决；C6 是开销较大的一个——其公开的范围（2 个 Concept / 3 个 Evidence / 1 个 Capsule / 6 步，约 40 秒）针对最小洗白链 *import → derive → derive → elevate* 加上合并交互进行了精简配置，超出该范围再增加一个元素或步骤就会超过 10 分钟的 SAT 预算。在范围内，检查对所有事件交错是穷尽的。

## 3. 套件 2 — 事务运行时的 TLA+/TLC 模型

`tla/KipTransactions.tla` 对并发客户端提交带有可选 `EXPECT VERSION` 守卫和幂等键 (§32–§36) 的写入批次进行建模。引擎的提交是一步原子操作（这是 §32.1 自身的假定要求）；模型所*检查*的是其上的协议逻辑。

### 规范符合模式 (`KipTransactions_spec.cfg`)

2 个客户端 × 2 个元素 × 3 个键 × 2 个值；**771,913 个不同状态**，全部 6 个不变式均成立：

| 不变式 | 含义 | 规范 |
| --- | --- | --- |
| `LogExpectationsConsistent` | 每个已提交的受守卫写入所观察到的版本恰好是其所期望的版本（无更新丢失） | §32.3 (12), §35.1, §35.5 |
| `AnswersConsistent` | 同一个幂等键永远不会返回两个不同的成功结果 | §34.3 |
| `SeqDense` | `space_seq` 稠密、单调，仅由发生状态变更的提交分配，且等于提交记录 (Commit Record) 的索引 | §32.8, §33.1, §36.1 |
| `IdemUniqueCommit` | 每个幂等键最多对应一条提交记录 (Commit Record) | §34 |
| `VersionsMatchLog` | `_system.version` 等于该元素已提交写入的次数 | §35.5 |
| `TypeOK` | 状态类型正确 | — |

### 错误注入模式 1：快照时验证 (`_toctou.cfg`)

在准备时快照（prepare-time snapshot）而非提交时状态（commit-time state）验证 `EXPECT VERSION`（§32.3 阶段 12 所禁止的做法）会产生一个 **5 状态的反例**：c1 获取版本 0 的快照并提交 `EXPECT VERSION 0`；c2 先提交（版本 → 1）；c1 的陈旧提交被接受——典型的更新丢失 (lost update)。这表明提交时重新验证的要求是承重核心，而非代码风格。

### 错误注入模式 2：no_effect 未留存 (`_noretain.cfg`)

仅在幂等键下留存*引发状态变更*结果的实现（对 §32.8 + §33.1 的可能误读）违反了 §34.3：submit(k) → `no_effect`；另一个事务改变了状态；使用相同字节重试 retry(k) 此时*成功提交*。同一个键产生了两个不同的成功结果。**这就是发现 F2**——见 §6。

## 4. 套件 3 — 治理评估判定过程

`governance/check_governance.py` 将 §30（拒绝优先、协议不变式覆盖策略、默认拒绝）形式化为一个纯判定过程，并在有界完备域（90 条带通配符范围的候选规则 × 28 个请求 × 规则集大小上限为 2 的所有组合 × 所有排列 × 所有 1 规则扩展——共 **10,939,388 次判定检查**）上进行了穷举检查：

| 性质 | 含义 | 结果 |
| --- | --- | --- |
| P1 全域性 (Totality) | 每个请求均被明确判定为允许 (allow) 或拒绝 (deny) | **成立** |
| P2 顺序无关性 (Order-independence) | 策略规则*列表*的行为等同于规则*集合* | **成立** |
| P3 拒绝单调性 (Deny-monotonicity) | 添加一条拒绝规则绝不会将 deny 翻转为 allow | **成立** |
| P4 允许无法覆盖拒绝 (Allow-cannot-override) | 显式拒绝 / 不变式拒绝在添加任何允许规则后依然有效 | **成立** |
| P5 不变式至高性 (Invariant supremacy) | §30.3 协议非法操作在*任何*策略下均被拒绝 | **成立** |
| P6 重复幂等性 (Duplicate idempotence) | 重复添加同一条规则不会产生任何改变 | **成立** |

这些是 §30 所依赖但未曾明确陈述的性质；现在根据对评估顺序的自然解读，它们在经过检查的构建中均得到保证。

## 5. 套件 4 — EBNF 文法一致性

`grammar/check_ebnf.py` 解析了三种 ISO-14977 风格的文法：

| 检查项 | KQL (77 条规则) | KML (106 条规则) | META (109 条规则) |
| --- | --- | --- | --- |
| G1 格式良构性 | ok | ok | ok |
| G2 无重复定义 | ok | ok | ok |
| G3 无未定义非终结符 | ok | ok | ok |
| G4 起始符号可达所有规则 | ok | ok | ok |

跨文法检查 (G5)：60 个共享非终结符。三组别名在定义上验证为等价（`meta_value` ≡ `scalar_or_parameter` ≡ `scalar_value`；`structural_field` ≡ `schema_symbol`）。存在两处真实但符合预期的差异，目前已固定在经过审查的白名单中：

- `proposition_tuple` — 仅 KQL 允许原始谓词*路径表达式*；KML/META 要求精确的 `predicate_atom`（见已记录的 KQL 文法决策 4）；
- `where_clause` — 仅 KQL 具有 `BELIEF` / `BELIEF SLOT` 模式（投影属于查询端；变更语言没有信念匹配）。

共享规则中的任何*新增*漂移现在都将导致 CI 失败。有关规范清理的建议见 F4。

## 6. 发现项

> **状态**：以下建议已于 2026-08-15 在添加本报告的同一变更集中应用——规范 §11.1 / §29.6 / §34.3 (中英文版)、三个文法头部、`KIPSyntax.md` (中英文版) 以及 `design/KIP-2.0-Transactions.md` §17 (中英文版)。

### F1 — §11 概念合并允许解析环（规范性缺陷）

§11.1 仅约束了合并的*源*（“A 未被合并过”甚至未明确写出——模型对此作了善意假定）。没有任何规定禁止先将 A→B 合并，然后再将 B→A 合并：Alloy 在两次合并事件中就触发了该环（见证 R2），此后规范解析（`沿 merged_into 追踪至不动点`）将永不终止，`canon[]` 变为未定义——这将对 §12.3 规范命题标识、§11.4 碰撞整合以及任何通过合并链解析引用的实现产生连锁反应。

**建议**：在 §11 中补充——“合并绝不能在 `merged_into` 中造成环；如果合并的目标（通过传递关系）解析到源自身，运行时必须拒绝该合并。”防环变体已被验证为无环 (C5)。

### F2 — §32.8 与 §34.3 的交互未充分说明（说明性澄清）

§34.3 要求对重复键返回“原始留存的事务结果”，这预设了该结果已被留存。§32.8 规定 `no_effect` 事务不分配 `space_seq`，而 §33.1 仅将提交记录 (Commit Record) 附加到产生状态变更的提交上。如果实现者据此推断 `no_effect` 结果因此无需进行幂等留存，就会引入被 TLC 机械化发现的违反 §34.3 的缺陷（套件 2，模式 2）。

**建议**：在 §34 中补充一句话：“留存适用于每一个已定稿的结果，包括 `no_effect`；`no_effect` 结果必须像任何已提交结果一样被留存和重放。”（至于*中止*的事务是否被留存同样未作说明，值得补充一句明确说明；模型将中止视为未留存。）

### F3 — 派生写入时必须重新验证同空间闭包（实现指导）

Alloy 模型的早期版本仅在主要创建路径上检查了 §5.3 闭包；检查器随即生成了一个派生断言，其命题位于外部空间中（C4 反例）。规范本身并没有错——§5.3 全局声明了该闭包——但在 §29.6 的 `derive` 义务列表（密级传播、来源保留、权限不放大）中未提及引用闭包，而派生/推理写入恰恰是实现中最容易漏掉重新验证的地方。

**建议**：在 §29.6 或 §32.3 阶段 10 的验证描述中明确指出同空间闭包适用于*所有*写入路径，包括派生写入和维护写入。

### F4 — 同名但不同形态的文法规则（代码规范卫生）

`proposition_tuple` 和 `where_clause` 在三个文法中同名但形态存在有意差异；`scalar_value` / `scalar_or_parameter` / `meta_value` 形态完全相同却拥有三个名称。这两个方向都容易在未来的编辑中引入无意识的漂移。

**建议**：要么重命名有差异的规则（例如 KQL 的 `raw_proposition_tuple`）并统一别名名称，要么在 CI 中保留 `grammar/check_ebnf.py`，使经过审查的白名单成为允许差异的唯一权威来源。

### 值得陈述的积极保证

- §23 认识独立性机制完全达到了 `post/Knowledge_Experience_Memory_Skill.md` 的要求：复制/摘要/派生链无法造出佐证 (C7 + R4)，且循环来源无法放大支持度，因为引擎验证的谱系在构建上是无环的，而导入的声称谱系会坍缩为单一胶囊根。
- 源头/权限安全核心 (Architecture §16, Spec §31.5) 在范围内具有归纳可靠性 (C6)，且被证实是承重核心 (R3)。
- §30 治理评估顺序是汇聚的：策略表现为集合而非列表。

## 7. 有意未验证的内容

- **信念/投影策略、置信度公式、遗忘曲线、排序** — 规范有意未对它们做具体规定 (Architecture §2 非目标)；没有需要验证的规范性内容。仅对其框架属性（例如 §21.2 投影是只读的）进行了建模。
- **作为行为的记忆 (§4.4) 与学习 (§4.7)** — 这些是 Brain + 模型系统的实证属性；规范自身指出正确的检验工具是消融基准测试（§21.3 相关，Architecture §21.3），而非形式化证明。
- **物理清除 (§19.3, §29.7)** — 排除在 Alloy 范围之外（`Live` 是单调的）；将审计清除建模留作未来工作。
- **胶囊规范化/摘要 (§37.7)** — 确定性序列化属于测试向量问题（一致性套件的工作），而非模型检测问题。
- **密码学性质** — 假定签名是正确的；§37.8 中的“完整性 ≠ 真实性”分离在权限模型中通过结构化方式强制实施。

## 8. 复现步骤

```bash
export ALLOY_JAR=/path/to/org.alloytools.alloy.dist.jar   # Alloy ≥ 6.2
export TLA_JAR=/path/to/tla2tools.jar
v2/formal/run.sh
```

需要 Java 17+ 和 Python 3.10+。该脚本对每个证明目标的*预期*结果进行了断言——包括注入错误配置确实会产生反例——因此只要运行结果全绿，就意味着上述所有结论依然成立。
